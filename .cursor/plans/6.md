Implement **Phase 6 — Memory** for the Multi-Agent Studio.

This phase is primarily a **backend/runtime architecture phase**.

The UI is secondary.

The goal is NOT to simply attach a vector database to every agent.

The goal is to build a robust, extensible memory subsystem that allows agents and workflows to:

* retain useful state during execution
* remember important information across runs
* retrieve relevant memories efficiently
* distinguish different kinds of memory
* avoid unlimited memory growth
* avoid injecting irrelevant memories into prompts
* support shared and agent-specific memory
* work regardless of whether the agent backend is API, CLI, or local
* integrate cleanly with LangGraph and the existing `AgentRuntime`
* expose memory operations through the existing `RunEvent` architecture

Before implementing anything, inspect the current project carefully.

Especially inspect:

* Agent domain model
* `AgentBackend`
* `AgentExecutor`
* `AgentRuntime`
* WorkflowDefinition
* LangGraph compiler / graph builder
* Run / RunEvent architecture from Phase 4
* Agent Detail Page implementation
* existing memory-related types
* persistence architecture
* PostgreSQL/database setup if present
* existing repository/service patterns
* current dependency injection/service construction
* existing API routes

Do not introduce a parallel architecture.

Prefer extending existing runtime boundaries.

---

# 1. Core Architecture

Target architecture:

```text
                    ┌─────────────────────────┐
                    │      LangGraph          │
                    │     StateGraph          │
                    └────────────┬────────────┘
                                 │
                                 ↓
                         AgentRuntime
                                 │
              ┌──────────────────┴──────────────────┐
              │                                     │
              ↓                                     ↓
        AgentExecutor                         MemoryService
              │                                     │
      API / CLI / Local                    ┌────────┴────────┐
                                           ↓                 ↓
                                    Short-Term         Long-Term
                                      Memory              Memory
                                           │                 │
                                           ↓                 ↓
                                   Checkpoint/State     Memory Store
                                                         │
                                              ┌──────────┼───────────┐
                                              ↓          ↓           ↓
                                           Semantic   Episodic   Procedural
```

Important separation:

```text
LangGraph = orchestration

AgentRuntime = agent execution boundary

AgentExecutor = how the agent executes

MemoryService = how memory is stored/retrieved/managed
```

Do not put memory implementation inside:

* React components
* AgentExecutor implementations
* LangGraph compiler directly
* API routes
* provider-specific SDK code

---

# 2. Short-Term vs Long-Term Memory

Treat these as separate systems.

## Short-Term Memory

Short-term memory belongs to the current execution/thread/session.

Examples:

* conversation messages
* intermediate workflow state
* temporary tool results
* current plan
* current task context
* outputs from previous nodes in the same run

Scope:

```text
Run / Thread / Session
```

It should disappear or become inaccessible as active context when the run/thread ends unless intentionally promoted into long-term memory.

## Long-Term Memory

Long-term memory survives across runs.

Examples:

* user preferences
* known facts
* recurring patterns
* lessons from previous tasks
* successful strategies
* failure patterns
* reusable procedures

Scope may be:

```text
Agent
User
Organization
Workflow
Project
Global
```

Do not mix short-term state directly into the long-term store.

---

# 3. Memory Types

Long-term memory should distinguish at least:

```ts
type MemoryKind =
  | "semantic"
  | "episodic"
  | "procedural";
```

Do not treat all memory as generic text chunks.

---

# 4. Semantic Memory

Semantic memory represents facts and knowledge.

Examples:

```text
"The project uses pnpm."

"The user prefers TypeScript."

"The backend uses PostgreSQL."

"The deployment target is Linux."
```

Semantic memory should support:

* structured facts
* natural-language content
* metadata
* embeddings when useful
* updates
* confidence
* source tracking
* timestamps

Recommended conceptual structure:

```ts
interface SemanticMemory {
  id: string;

  kind: "semantic";

  namespace: MemoryNamespace;

  subject?: string;

  content: string;

  structuredData?: Record<string, unknown>;

  importance: number;

  confidence?: number;

  source?: MemorySource;

  createdAt: string;
  updatedAt: string;

  embedding?: number[];

  metadata?: Record<string, unknown>;
}
```

Do not require every semantic memory to have an embedding.

---

# 5. Episodic Memory

Episodic memory represents past experiences.

Examples:

```text
"During run X, the coder modified auth middleware and tests failed because the migration had not been applied."

"Research Agent searched three sources and source B turned out to contain the correct answer."

"The previous deployment failed after dependency installation."
```

It should allow an agent to answer:

```text
Have I encountered something similar before?
```

Recommended fields:

```ts
interface EpisodicMemory {
  id: string;

  kind: "episodic";

  namespace: MemoryNamespace;

  runId?: string;
  workflowId?: string;
  agentId?: string;

  situation: string;

  action?: string;

  result?: string;

  lesson?: string;

  success?: boolean;

  importance: number;

  createdAt: string;

  embedding?: number[];

  metadata?: Record<string, unknown>;
}
```

Do not simply copy every RunEvent into episodic memory.

Run history and memory are different concepts.

Only useful experiences should become memories.

---

# 6. Procedural Memory

Procedural memory represents reusable behavior, strategies, rules, or instructions.

Examples:

```text
"When modifying this repository, run pnpm lint before tests."

"For authentication bugs, inspect middleware before route handlers."

"When researching technical issues, prioritize official documentation."
```

Conceptually:

```ts
interface ProceduralMemory {
  id: string;

  kind: "procedural";

  namespace: MemoryNamespace;

  title?: string;

  procedure: string;

  trigger?: string;

  importance: number;

  confidence?: number;

  createdAt: string;
  updatedAt: string;

  metadata?: Record<string, unknown>;
}
```

Procedural memories may later be used to improve prompts or agent behavior.

Do not automatically rewrite the Agent's system prompt every time procedural memory changes.

---

# 7. Memory Namespace

Every long-term memory MUST belong to a namespace.

Do not create one global unscoped vector collection.

Design something conceptually similar to:

```ts
interface MemoryNamespace {
  organizationId?: string;
  userId?: string;
  projectId?: string;
  workflowId?: string;
  agentId?: string;
}
```

Actual fields should follow the current product/domain model.

Examples:

```text
agent/{agentId}

workflow/{workflowId}

project/{projectId}

user/{userId}

organization/{organizationId}
```

The retrieval layer must be able to restrict searches to allowed namespaces.

# 8. Memory Visibility / Sharing

Support memory visibility explicitly.

Conceptually:

```ts
type MemoryVisibility =
  | "private"
  | "workflow"
  | "project"
  | "organization"
  | "shared";
```

Do not assume every agent can read every memory.

An agent should normally access:

```text
its own memory
+
explicitly shared memory
+
workflow/project memory permitted by policy
```

Design this so access-control rules can become stricter later.

# 9. MemoryService

Create a central backend service.

Conceptually:

```ts
interface MemoryService {
  remember(input: RememberMemoryInput): Promise<Memory>;

  recall(
    query: RecallMemoryQuery
  ): Promise<MemorySearchResult[]>;

  get(id: string): Promise<Memory | null>;

  update(
    id: string,
    update: UpdateMemoryInput
  ): Promise<Memory>;

  forget(id: string): Promise<void>;

  list(
    query: ListMemoryQuery
  ): Promise<Memory[]>;

  consolidate?(
    query: MemoryConsolidationInput
  ): Promise<MemoryConsolidationResult>;
}
```

AgentRuntime must depend on this abstraction.

It must not depend directly on pgvector, PostgreSQL, or a specific vector database.

# 10. Storage Abstraction

Introduce a storage boundary.

Conceptually:

```ts
interface MemoryStore {
  insert(memory: Memory): Promise<void>;

  update(memory: Memory): Promise<void>;

  delete(id: string): Promise<void>;

  get(id: string): Promise<Memory | null>;

  search(
    query: MemoryStoreQuery
  ): Promise<MemorySearchResult[]>;
}
```

Initial implementation should preferably use the project's existing database.

If PostgreSQL is already available, prefer:

```text
PostgreSQL
+
pgvector
```

rather than introducing a completely separate vector database without a strong reason.

However, keep `MemoryStore` independent from PostgreSQL.

Future implementations should be possible:

```text
PostgresMemoryStore
QdrantMemoryStore
PineconeMemoryStore
InMemoryMemoryStore
```

without changing AgentRuntime.

# 11. Do Not Use Vector Search for Everything

Memory retrieval must not mean:

```text
embed query
↓
topK cosine similarity
↓
inject everything into prompt
```

Implement a retrieval pipeline.

Target:

```text
Memory Query
     ↓
Namespace Filter
     ↓
Metadata / Type Filter
     ↓
Candidate Retrieval
     ↓
Semantic / Lexical Retrieval
     ↓
Scoring
     ↓
Re-ranking
     ↓
Deduplication
     ↓
Budget Selection
     ↓
Returned Memories
```

---

# 12. Hybrid Retrieval

Prefer hybrid retrieval architecture.

Support combining:

```text
semantic similarity
+
metadata filters
+
recency
+
importance
+
exact / lexical matching
```

Do not make embedding similarity the only relevance signal.

Conceptually calculate:

```ts
score =
    semanticWeight * semanticSimilarity
  + recencyWeight * recencyScore
  + importanceWeight * importance
  + lexicalWeight * lexicalScore
  + contextWeight * contextualRelevance;
```

Do not hard-code arbitrary weights throughout the codebase.

Create a retrieval/scoring configuration.

# 14. Retrieval Query

Conceptual query:

```ts
interface MemoryRetrievalQuery {
  text: string;

  namespace: MemoryNamespace;

  kinds?: MemoryKind[];

  limit?: number;

  minScore?: number;

  maxTokens?: number;
```

# 15. Memory Context Budget

Memory injection must have an explicit budget.

For example:

```ts
interface MemoryContextBudget {
  maxMemories: number;
  maxTokens: number;
}
```

The runtime must not allow memory to consume the entire LLM context window.

Selection should prioritize highest-value memories until the budget is reached.

# 18. pgvector Strategy

If PostgreSQL is available, implement vector storage using pgvector.

Prefer a schema where relational metadata remains queryable normally.

Conceptually:

```text
memories
├── id
├── kind
├── namespace fields
├── content
├── structured_data
├── importance
├── confidence
├── source
├── created_at
├── updated_at
├── expires_at
├── embedding
├── embedding_model
└── metadata
```

Do not serialize the entire memory record into a single opaque vector-store blob.

Use PostgreSQL columns / JSONB appropriately.

---

# 19. Vector Index

If dataset size justifies approximate nearest-neighbor indexing, support a pgvector ANN index.

Prefer HNSW as the initial default unless current deployment constraints strongly favor another index.

Keep index configuration in database/infrastructure code, not application business logic.

Do not prematurely optimize for millions of memories.

Make exact vector search possible for testing/relevance evaluation.

# 20. Memory Write Policy

This is one of the most important parts of this phase.

DO NOT store every message, output, or event as long-term memory.

Create a `MemoryWritePolicy`.

Conceptually:

```ts
interface MemoryWritePolicy {
  shouldRemember(
    candidate: MemoryCandidate
  ): Promise<MemoryWriteDecision>;
}
```

Decision:

```ts
interface MemoryWriteDecision {
  remember: boolean;

  kind?: MemoryKind;

  importance?: number;

  reason?: string;
}
```

Memory candidates may come from:

```text
agent result
user message
tool result
workflow outcome
run failure
human feedback
```

But only useful information should be promoted.

---

# 21. Memory Extraction

Create a memory extraction boundary.

Conceptually:

```ts
interface MemoryExtractor {
  extract(
    input: MemoryExtractionInput
  ): Promise<MemoryCandidate[]>;
}
```

The extractor may initially use deterministic rules and/or an LLM.

Do not bury extraction prompts inside AgentRuntime.

Keep extraction prompts/configuration isolated.

---

# 22. Hot-Path vs Background Memory Writing

Support the architecture for two write modes:

```text
Hot Path
Background
```

## Hot Path

Memory extraction happens during agent execution.

Use only when memory is immediately needed.

Advantages:

```text
new memory immediately available
```

Disadvantages:

```text
extra latency
extra model cost
```

## Background

Execution completes first.

Memory extraction/consolidation happens afterward.

Prefer this for most long-term-memory creation where immediate availability is unnecessary.

For this phase, background processing can remain an application-level async job abstraction.

Do not build a distributed queue system solely for this feature.

---

# 23. Memory Importance

Every long-term memory should support importance.

Example normalized range:

```text
0.0 – 1.0
```

Importance can reflect:

* explicit user preference
* repeated information
* successful strategy
* high-impact failure
* durable project fact
* direct user instruction

Do not equate importance with semantic similarity.

---

# 24. Recency

Implement recency scoring.

Recent memories may be more useful, but recency must not completely override highly important durable information.

Keep recency calculation encapsulated.

Example conceptual decay:

```text
recencyScore = decay(age)
```

Do not scatter date math throughout retrieval code.

---

# 25. Reinforcement / Access Tracking

Track memory usage where useful.

Possible fields:

```text
lastAccessedAt
accessCount
reinforcementCount
```

When a memory proves useful, allow its effective importance to increase.

Do NOT update records on every read if that creates excessive database writes.

Batching or selective reinforcement is acceptable.

---

# 26. Duplicate Detection

Avoid accumulating equivalent memories.

Before storing a new semantic/procedural memory, detect probable duplication.

Possible strategy:

```text
candidate
    ↓
exact normalized comparison
    ↓
semantic similarity
    ↓
existing memory?
      ↓
update / merge / insert
```

Do not blindly create:

```text
User uses pnpm
User prefers pnpm
Project uses pnpm
The package manager is pnpm
```

as four independent memories when they represent the same durable fact.

---

# 27. Memory Update / Merge

Support memory evolution.

A new memory may:

```text
insert
update
merge
supersede
contradict
```

Do not assume memory is immutable.

Example:

Old:

```text
The project uses npm.
```

New:

```text
The project migrated to pnpm.
```

The system should eventually represent the new state rather than retrieving both as equally valid facts forever.

---

# 28. Contradiction Handling

Support basic contradiction metadata.

Conceptually:

```ts
supersedesMemoryId?: string;
supersededByMemoryId?: string;

```

Do not build a full knowledge graph inference engine.

But ensure stale facts can be retired.

* manual deletion

# 31. Memory Consolidation

Implement or prepare a `MemoryConsolidator`.

Purpose:

```text
many similar low-level memories
             ↓
        consolidated memory
```

Example:

```text
Run 1: user asked for concise output
Run 4: user preferred short explanation
Run 8: user requested fewer details
```

may become:

```text
User generally prefers concise answers.
```

Do not run consolidation synchronously on every memory write.

# 32. Episodic → Procedural Promotion

Support the future ability to learn strategies from repeated experiences.

Example:

```text

Episode 2: same pattern
Episode 3: same pattern
             ↓

"When debugging authentication, inspect middleware first."
```

Implement the boundaries necessary for this, but a sophisticated learning algorithm is not required in Phase 6.

Conceptually:

```text

```

Do not store LangGraph checkpoints as semantic long-term memories.

# 40. Memory Prompt Injection Protection

Treat retrieved memory as untrusted contextual data.

Memory content must not silently become system-level instructions.


Especially important when memory originates from:

```text

tools
```

# 50. Concurrency

Memory writes may occur from parallel LangGraph branches.

Handle this safely.

Potential problems:

```text
duplicate insertion
simultaneous update
lost merge
```

Use database transactions/constraints where appropriate.

Do not rely purely on frontend state.

---

# 51. Idempotency

Memory extraction from retries must not create duplicate memories.

Use idempotency keys where appropriate, potentially derived from:

```text
runId
nodeId
source event
candidate identity
```

Retries should not multiply identical long-term memories.

---

# 52. Failure Behavior

Memory should usually degrade gracefully.

If long-term retrieval fails:

```text
agent execution should normally continue
```

unless the workflow explicitly declares memory mandatory.

Emit/log the failure.

Do not crash every agent execution because pgvector or embedding generation temporarily failed.

Likewise, failure to persist a non-critical memory after execution should not convert an otherwise successful Run into a failed Run unless configured as required.

---

# 53. Performance

Avoid:

```text
embedding every message multiple times
querying memory repeatedly within the same node
loading entire memory tables
retrieving vectors without namespace filters
```

Use batching/caching where useful.

Do not prematurely introduce Redis unless the project already needs it.

---

# 54. Security and Isolation

Memory is backend data.

Enforce namespace isolation server-side.

Never trust:

```text
agentId
workflowId
organizationId
```

coming from the browser as proof of authorization.

Do not expose another user's/organization's memories through search.

Even if authentication is currently minimal, keep the repository/service architecture compatible with proper authorization.

---

# 55. Data Deletion

Design memory records so project/user/agent deletion can cascade or clean up appropriately.

Avoid orphaned memory records.

If embeddings are stored separately, deleting memory must also remove associated embeddings.

---

Do not create unnecessary layers if equivalent boundaries already exist.

The important thing is dependency direction:

```text
Domain
  ↑
Application
  ↑
Infrastructure adapters
```

Business logic should not depend directly on PostgreSQL-specific code.

# 59. Explicit Non-Goals

Do NOT build:

* a generic RAG platform
* a document knowledge-base system
* a full knowledge graph
* autonomous prompt rewriting
* unrestricted cross-agent memory
* separate vector databases per agent
* a full Memory Explorer frontend
* Redis-based distributed memory architecture
* distributed background workers solely for memory
* complex ML-based learned ranking
* infinite conversation transcript storage
* automatic storage of every RunEvent

# 60. Critical Design Rules

These rules are mandatory:

### Rule 1

Memory is not chat history.

### Rule 2

Run history is not long-term memory.

### Rule 3

Not every event deserves to become memory.

### Rule 4

Vector similarity alone is not sufficient retrieval.

### Rule 5

Memory must be scoped by namespace.

### Rule 6

Memory retrieval must respect a context/token budget.

### Rule 7

Embedding provider must be independent from AgentBackend.

### Rule 8

AgentExecutor must not own memory persistence.

### Rule 9

LangGraph compiler must not query the memory database directly.

### Rule 10

Retrieved memory must be treated as contextual data, not system-level instructions.

### Rule 11

Memory must support update, superseding, and deletion.

### Rule 12

Backend memory failures should normally degrade gracefully.

---

# 61. Definition of Done

Phase 6 is complete when:

1. Short-term and long-term memory are separate concepts.
2. LangGraph execution can persist and restore appropriate short-term state.
3. Long-term memory has a stable domain model.
4. Semantic memory works end-to-end.
5. Episodic/procedural memory are either implemented or cleanly supported by the architecture.
6. Memories have explicit namespaces/scopes.
7. AgentRuntime can retrieve relevant memory before execution.
8. AgentRuntime can create memory candidates after execution.
9. Long-term memory is not populated indiscriminately.
10. Retrieval uses more than vector similarity alone.
11. Retrieval respects namespace and metadata filters.
12. Retrieval respects a context/token budget.
13. Embedding generation is abstracted from the agent's execution backend.
14. Current API, CLI, and local AgentBackend architecture remains compatible.
15. Memory operations emit existing RunEvents.
16. Duplicate memories are controlled.
17. Memories can be updated/deleted/superseded.
18. Memory access is isolated by scope.
19. Parallel/retried workflow execution does not corrupt memory.
20. Memory infrastructure failures normally degrade gracefully.
21. Retrieval behavior has meaningful tests/evaluation fixtures.
22. UI remains a thin configuration/inspection layer over the backend subsystem.
23. No React Flow or frontend component directly manages memory storage.
24. No provider-specific memory implementation leaks into AgentRuntime.
25. Future memory stores/retrievers/embedding providers can be added without redesigning agents or workflows.

# 62. Before Coding

Before modifying the repository:

1. Inspect all existing memory-related code.
2. Inspect the current database/persistence stack.
3. Inspect AgentRuntime and AgentExecutor.
4. Inspect how LangGraph state/checkpointing is currently configured.
5. Inspect RunEvent definitions.
6. Identify what can be reused.
7. Identify schema migrations required.
8. Produce a concise implementation plan.
9. Then implement incrementally.

Do not rewrite working functionality from Phases 1–5.

Prefer a focused, backend-first memory subsystem that integrates with the existing architecture.
